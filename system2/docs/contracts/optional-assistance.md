# Optional assistance and calibration

The workflow works without a model service. No provider is enabled or selected automatically. Local proposals, evidence inspection, correction, both acceptance stages and delivery remain available when assistance is disabled or fails.

## Configuration

System2 reads `config/model-provider.local.json`; System1 reads `Code/config/model-provider.local.json`. Both are ignored by version control. Sanitized examples in those directories are disabled. A deployment owner must configure a specific HTTPS JSON gateway, model, credential environment variable, permitted evidence and request limits before enabling it. No credentials belong in JSON or history. The gateway is a replaceable adapter contract, not a claim that an arbitrary vendor's native API accepts this JSON.

System2 sends `evidence-suggestions/1` with `model`, `capability` and explicitly allowlisted evidence objects. Capabilities are `structure_review` and `requirement_candidates`; candidates are requested only after the content gate. Each evidence ID is `document_id:unit_id`. The gateway returns `suggestions`, each citing `evidence_ids` from the sent set. Structure and candidate suggestions remain separate from Canonical, scores and acceptance. The button “Get optional assistance” triggers one bounded request; nothing is sent on opening a source.

System1 sends `source-assessment-suggestions/1` with configured metadata fields for explicitly allowed source IDs. Returned suggestions name a five-dimension field, HIGH/MEDIUM/LOW rating, reason and supported `evidence_fields`. They remain proposals for human verification. `max_calls` applies to the explicit assessment batch; System2 sends at most one call per assistance request. `max_bytes` limits each sent JSON body, response length is bounded, timeout is at most 60 seconds, and redirects are refused. HTTP failure, limits, invalid configuration or unsupported citations return the local/manual path.

## Independent calibration

`verification/calibration.py` accepts frozen predictions and independent human labels from a calibration split. It records prediction/label hashes, format/language/judgment scope, method version and per-bin Wilson lower bounds. These conservative routing values are not source accuracy guarantees. An evaluation must separately measure Requirement precision, recall, field correctness and relationship correctness on held-out real sources. Training/calibration evidence is not held-out acceptance evidence.

System2 optionally reads `config/scoring-rules.local.json`. Its `source_languages` maps exact source hashes to independently identified language. Each rule binds `source_sha256`, `unit_id`, `original_sha256`, `stage`, `aspect`, fixed scoring `method`, `score` and `calibration_path` inside the configuration directory. Requirement rules additionally bind `proposal_sha256` to the current local classifier proposal. Content requires `text`, `coverage`, `structure` and `order`; Requirement requires `classification`, `association` and `subdivision`. The calibration artifact must match format, language, stage, aspect and method; its content hash is checked. Missing scope, unmatched rules or missing parts never produce automatic acceptance. These are evaluation-owned frozen inputs, never API response fields.

After validation, each persisted Requirement score retains `rule_binding` with schema `requirement-score-binding/1`, classifier method, original-unit hash and proposal hash. Recalculation and dimension display validate that binding against the current proposal. A missing or mismatched binding yields no current supported score; the recorded score parts remain unchanged for audit. Method reconciliation suspends obsolete machine delivery and records a version event once. Named human decisions remain valid when their source/content dependencies are unchanged, while obsolete machine confidence is no longer displayed as current. This does not grant calibration or activate scoring rules.

System1 reads `Code/config/machine-assessment-rules.local.json`, an array of independently validated rules bound to source ID, source revision, source hash and dimension. Each carries rating, confidence, method, evidence and calibration version. Without valid rules, dimensions stay UNKNOWN. Exact verified snapshot identity can establish only the traceability dimension; it does not establish authority, relevance, currency or access permission. All five HIGH judgments, independently adequate confidence and original System1 hard gates are necessary for automatic INCLUDE. Named human decisions and human draft/report holds take precedence. Old workbook H/M/L ratings never acquire invented confidence.

No real API or production calibration is configured by this implementation. Failure-path tests and synthetic calibration fixtures validate plumbing only. Real provider effectiveness and English/Norwegian calibration require separate acceptance records.
