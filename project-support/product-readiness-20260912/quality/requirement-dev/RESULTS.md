## Implementation and safety boundaries

- `classification_evidence.py` recognizes explicit `Rationale` section prefixes, the source question heading `How do I interpret this requirement?`, or the nearest actual source heading with that literal role. Merely mentioning a rationale does not create a context role. A nearer different heading stops role inheritance.
- A unit mixing explicit context with a numbered/formally labelled clause, another classification-bearing field, or a conflicting table/standard role stays `undetermined` with its normative matches retained. No automatic textual deletion occurs.
- `effective.resolve` retains located header cells from the effective owning table before narrowing to a selected row. These are read-only source-context evidence, not new editable business fields.
- A nominal row becomes a candidate only beneath unambiguous, disjoint `Indicator` and `Requirement` headers, with nonempty same-row content/value and matching source cell references. Missing headers, arbitrary value columns, a number alone, a bare Yes, cross-row spans, overlaps and missing references abstain. No numbering-only rule was added.
- Every new proposal keeps `confidence: null`. Existing method/proposal score binding prevents old scores from accepting a new method. Named human decisions remain separate and take precedence.

No runtime/business database was loaded or changed by this task. No candidate was adopted, no current material content confirmed, and no Requirement business review was performed.

## Minimal integration boundary after the passage-decomposition clarification

Read-only assessment, 2026-09-13. The user's one-passage/multiple-Requirements direction and explicitly confirmed `object` (the action target) are authoritative in [System3 DESIGN](../../../../system3/DESIGN.md#user-clarification-passage-to-requirement-decomposition). This section proposes a bounded identification adapter, not a new schema, connected third pane or semantic implementation.

**Reusable code and limits.** `models/requirement.py` already has a list of `conditions`, separate exceptions/exemptions/negations/modalities, exact source text anchors, scoped references to clauses/Requirements/actions, clause parents and `joins_next`, and source-bound client/auditor action text. `canonical.py`, `semantics.py` and `clauses.py` derive these from role-aware native source regions. They provide source-preserving building blocks; the presence of those fields and existing tests does not prove accurate decomposition on current material input. A `RequirementClause` is a clause inside one Requirement, not automatically another Requirement. The richer model does not expose a universal per-Requirement verb plus object/objective field; client/auditor action lists cannot simply be relabeled as that field. The separate `domains/regulatory` projection has `action` and `object`, but extracts a first modal/action/remainder and a singular condition. That projection is insufficient for multiple actions, shared qualifiers and multiple condition scope.

`review/requirement_subdivision.py` is also reusable: existing explicit human subdivision requires exact, nonoverlapping accepted-text spans, a complete-parent review and reason, explained unassigned text, and a basis hash over source, unit version and resolved view. It preserves the whole parent/context, versioned child identities and residual spans; output is explicitly `PROVISIONAL` with peer confirmation pending. This is a safe manual span-decision mechanism, not an automatic decomposer. Its nonoverlapping spans cannot directly represent a shared condition included in two children, and it has no per-child verb/target/condition editor contract. Preserve parent context and explicit links rather than copying shared text into misleading independent spans.

**Smallest explicit identification path, proposed only.**

1. The user selects a checked range and explicitly starts **Identify Requirement candidates** against the currently adopted, confirmed master content. The server must resolve that master and its confirmation, reject stale source/content and unresolved source follow-up, and authorize the operation; a personal content confirmation alone is not master adoption. `review/material_processor.py::input_envelope` already binds `material_id`, source `source_id/snapshot_id/content_hash`, confirmed `input_revision`, selected `scope`, ordered blocks/dependency closure, `input_hash`, confirmer and `request_id`. It does not itself choose a master branch, check all current source-governance issues, persist a job, or provide idempotency. Those remain adapter responsibilities, with the master revision/confirmation identity captured alongside this existing envelope and checked again at review/application.
2. Assemble legacy classifier units from that frozen content, preserving block IDs and source refs. A text unit uses exact text; headings are source context; a table candidate uses an explicit same-row Indicator/Requirement pair and located headers. Preserve parent headings, checked cross-page continuations, table cells and footnote dependencies. Maintain character-offset mappings across joined fragments because classifier match offsets refer to assembled text. Images, missing native text, ambiguous order/merges or unsupported structures become visible unresolved coverage. Do not manufacture canonical PDF bounding boxes for HTML/Excel input or let heading keywords alone establish a formal obligation.
3. Call existing `classification.propose` with actual recovered assembly, retaining all classification results, evidence, method version, abstentions and null confidence. Produce separate pending **passage candidates** plus visible noncandidate/unresolved coverage. One classifier unit currently produces one classification proposal; it does not establish how many Requirements the passage contains. Do not promote modal matches, sentence count or existing table rows into final Requirement cardinality.
4. Persist a candidate batch with the exact envelope identity, adapter/assembly/classifier versions, unit spans and deterministic input/proposal fingerprints. A repeated request returns the same batch/receipt; a new confirmed content version creates a separate batch. Candidate review must bind batch ID, candidate ID, source/content hash, source spans and proposal version, with optimistic review revision and named human decision. Reuse legacy `requirement_scores` proposal binding and `WorkflowStore`'s separate content/Requirement statuses as guard patterns, not by silently importing work into its publication path. Editing source content invalidates the applicable binding while retaining prior decisions as history. Identification must not set master confirmation, Canonical `ACCEPTED`, formal semantic acceptance or publication.

`material_processor.capability/process` remain unavailable and `validate_output` supplies only generic identity/state/human-adoption guards. The generic payload slot is not an approved semantic schema. An eventual classification-only operation can use this safety envelope without claiming that verb/target/conditions are implemented, but its route, persistent review storage and UI remain unconnected today. No code or runtime changes were made for this assessment.

**Acceptance gaps that prevent a usable decomposition claim.** Source structure, passage identification, atomic Requirement splitting and semantic fields require separate evidence. This round's 39-unit development diagnostics supply correct source assembly; they do not measure actual material assembly or independent identification precision/recall. Complete source-positive/negative coverage is still required to meet the existing 90%/90% identification gate. Decomposition additionally needs source-first examples with zero/one/multiple Requirements, coordinated verbs, nominal limits/Yes rows, shared and action-specific conditions, nested AND/OR, negation, exceptions, cross-references and retained residual text. Freeze parent/child boundaries and all ambiguous cases before predictions, then report split/merge errors, verb/target exact evidence, condition membership/scope and logical-connector preservation separately. No decomposition threshold or business Gold has been established; these dimensions are **UNMEASURED**. A missing extracted condition must never mean unconditional applicability.

Recommended next experiment: use only development material to annotate 5–10 complete passages covering those cases, keep every source span and disagreement, and compare existing clause/subdivision/semantic helpers without modifying sources or declaring their `accepted` status a human decision. The action target is already confirmed as `object`; remaining design decisions concern shared-condition scope, recursive groups and counting. Those decisions block freezing the final field editor/semantic schema, but does not block source-fidelity repair, a classification-only offline experiment, or explicit passage-candidate review design. The material Process action and automatic semantic/downstream processing remain outside this assessment.
