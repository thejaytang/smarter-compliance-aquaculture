一、这轮工作的核心目标

本轮验收对象是系统本身的能力与质量，包括机器处理是否可靠、需要人工处理的事项是否被正确识别和递交、人工处理结果能否准确回流，以及这些结论是否有数据支持。

人工业务审核由用户和实际审查员承担。人工队列尚未清空、正式交付的 Requirement 数量为零，均不能单独作为系统未完成的依据。工程验收需要用隔离样本证明人工流程可用，不得代替真实审查员批量完成业务决定。

同时，不能把所有内容都送入人工队列后宣称自动化目标完成。必须分别说明机器完成了多少处理、能够安全自动通过多少内容、多少内容需要人工检查，以及其中多少确实需要修正。

长期项目目标保持不变。本轮集中形成一个边界明确、能够展示、能够复查的阶段版本，不扩大到 System3 的完整实现、Evidence 提取、具体场地匹配或最终合规判定。

二、执行时间与工作方式

从用户明确启动本目标时开始计时，争取六小时内形成交付，默认采用最多八小时的执行窗口。计时包括工具等待、测试、报告和视觉检查，不因跨会话重新开始。

启动目标后，可以直接开展既定范围内的可逆本地开发、缺陷修复、诊断实验和验证，不因常规工程选择反复请求确认。外部模型启用、材料外传、正式定时任务启用、受保护服务重启和其他已有授权边界继续有效。

先读取项目的 `AGENTS.md`、`README.md`、`PROJECT_STATE.md`、现有目标、接口合同和相关系统状态。复用已经成立的工程成果与有效证据，不重复已经完成的数据库迁移和来源审核，也不机械重启旧的 PDF 优化循环。

八小时是本轮交付截止时间，不是质量自动通过的条件。到时必须形成一个有明确结论的版本状态和交付包。若部分目标未达标，应交付可用的受限候选版本、实测报告和缺口说明，并保留整体目标未完成的状态，不能用文档完成代替系统达标。

三、各系统必须具备的能力

1. System1：来源治理与受控材料交接

保留已有来源身份、原件、版本、纳入决定、获取状态、人工操作和历史。来源缺失、访问受限、正文不完整或需要补充信息时，应生成原因明确、可以执行的人工事项。

说明来源如何进入系统、如何被纳入或排除、何时可以交给 System2，以及来源版本变化如何影响下游。

核实实际交接字段，包括来源标识、文件或地址、材料类型、来源版本、原件位置、纳入状态、获取完整性和处理状态。字段名称以真实接口为准，不为演示编造接口。

System1 的业务状态由所属数据库持久保存；Excel 是生成的来源台账和查看界面。

2. System2A：忠实还原原文

根据实际支持范围处理 PDF、HTML 和 XLSX。对不支持或不完整的材料提供明确、可恢复的处理路径。

PDF 处理应区分文本型、扫描型和混合型材料，保留正文、标题、编号、辅助文字、阅读顺序和原文位置。不能因为内容看起来与 Requirement 无关而提前删除。

表格需要保留整体证据、单元格内容、行列位置、合并关系、表头、表注、脚注及跨页联系。照片和示意图保留整图、图题和位置；扫描正文仍属于需要识别的内容。

原文核查必须覆盖“原文存在但完全没有生成输出”的区域，不能只检查已经抽取出来的条目。

每个结果应关联来源、版本、页码或区域、结构关系和核查状态。明确区分不可变原始事实、机器输出和经过版本化人工修正后的有效结果。

3. System2B：Requirement 判断与可追溯交付

基于已经通过相应内容核查的 A 结果及必要上下文，识别 Requirement，包括建议性条款，并分别检查误收、漏判和无法确定的情况。

保留原文依据、原始编号、来源版本、位置和共享上下文。对拆分后的条目保留父项、原文片段和生成标识，不能编造原文要求，也不能把父项和子项重复计数。

拆分粒度和计数方式仍属于可逆、可配置的临时策略，不得宣称已经获得同伴对最终业务语义的认可。

原文、A 的内容或共享上下文发生变化后，应使受影响的 B 判断和交付结果进入重审状态，同时保留旧历史和不受影响的结果。

四、统一人工工作台与自动处理边界

System1、A、B 共用一个正常人工入口。每项人工任务必须说清：

- 需要人决定或修正什么；
- 为什么进入人工队列，来自哪个阶段；
- 对应的原文、位置和必要上下文；
- 机器已经完成了哪些处理；
- 置信度、规则或核查证据从哪里产生；
- 哪些范围尚未验证或存在冲突；
- 人工提交后将改变哪些状态，并影响哪些下游结果。

内容核查采用左侧原文、右侧有效结果及上下文的方式。验证定位、补录、文本和表格修正、脚注与跨页关联、草稿恢复、历史查看及定向重审等实际操作。

人工确认、人工修正和机器置信度必须分别记录。不能把人工确认后可交付，改写成机器准确率百分之百。规则分数、模型自报分数和多智能体一致意见也不能直接当作经过校准的正确概率。

自动处理应同时具备原文关联、必要核查、明确阻断条件和可追溯记录。关键遗漏、错误数字或否定词、表格错位、关键脚注归属错误不能被平均分掩盖。

对机器未报警和自动通过的部分也要主动检查，测量漏报。全部 Pending 不能作为验证器准确发现问题的证据。

数据库保存决定和历史；Excel 单向生成，不作为正常审核输入，也不提供人工修改 Excel 后回写业务状态的路径。决定保存、Excel 待同步、同步完成和同步失败必须分开表示，保存决定不能等待整本 Excel 重写。

通过稳定标识、版本检查、重复提交保护、后台同步、失败重试和恢复机制，防止丢失决定、重复操作、旧结果覆盖新结果及虚假完成。

五、功能验收

建立功能矩阵，逐项区分“代码已实现”“日常实例已加载”“隔离样本已验证”“具有质量证据”和“剩余缺口”。只在隔离环境运行过的功能，不能直接计入日常实例已交付能力。

以下十六类关键场景必须逐项给出证据：

1. 从正常入口进入 System1、A、B，并确认实际连接和运行版本。
2. 查看来源决定和历史，在隔离副本中提交来源补充事项。
3. 沿实际入口处理或复用 PDF、完整 HTML 和 XLSX。
4. 正确处理正文缺失、材料不可用和不支持格式。
5. 发现并定位没有对应输出的原文区域，通过工作台补录。
6. 核查和修正扫描正文，保留原始图像证据。
7. 修正表格、合并关系、脚注归属和跨页关联。
8. 保存及恢复草稿，正确拒绝过期或不完整提交。
9. 保存 A 的审核结果和历史，仅解锁对应的 B 处理。
10. 修正 B 的误收和漏判，包含建议性条款。
11. 增加、修改和撤回临时子项，保持原文关联且不重复计数。
12. 修改内容或上下文后，触发准确的下游失效与重审。
13. 重复提交、冲突提交和隔离恢复后，不丢失或重复保存决定。
14. 验证 Excel 待同步、失败、重试、锁定解除和版本一致性。
15. 在隔离环境验证每周抽查机制及样本不足的处理。
16. 验证无外部 API 时的完整本地流程，以及外部增强失败后的受控回退。

十六项必须全部通过。涉及源文件或历史丢失、未解决问题被标成完成、主流程无法操作的缺陷属于硬阻断项。

每周抽查保留现有规则：System1 五条来源、A 二十个原文检查单元、B 五个分类判断，System3 不启用。A 的抽样必须能够发现完全遗漏的内容，B 同时覆盖正例和负例。验证机制不等于启用正式调度。

六、量化评估与样本设计

先冻结样本和第一版机器结果，再修复系统。记录来源、版本、页码、选样理由、配置、参考答案资格及样本是否已经用于开发。

本轮以现有授权材料开展诊断，不依赖用户先完成大规模业务审核：

- 对现有全部 System2 文档做处理状态盘点，保留失败和来源阻塞项。
- 从现有 CS004 PDF 选择八个物理页面，包含第十九至二十页及完整跨页窗口，覆盖正文、标题、编号、复杂表格和脚注。
- 调查这八页的全部可见原文区域，包括没有任何输出的区域。
- 文字对照至少包含一百个原文文字单元、两千个参考字符，以及实际存在的至少五十处关键数字、单位、日期、符号或否定表达。
- 表格评估至少包含两张完整逻辑表、一百个单元格、一组跨页关系、二十条阅读顺序关系和十条标题、脚注或延续关系。
- B 初始选择六十个完整原文判断单元，计划四十个来自 PDF、二十个来自三个已有完整 HTML 来源。争取包含至少二十个正例、其中十个建议性条款，以及二十个负例。必要时在调优前补充至最多八十个，原样本与补充样本分开报告。
- 临时拆分检查十个真实父项，在适用时覆盖至少二十个子项。
- 验证器增加十二个可控植入错误及对应未修改对照，覆盖完全遗漏、数字或单位、否定词、单元格归属、脚注或跨页关系、阅读顺序。
- 性能记录至少二十次读取、十次隔离保存和三轮导出或恢复过程。

缺少某类真实材料时明确记录缺口。合成扫描样本可以证明功能路径，不能代替真实扫描 PDF 的质量证据。

参考对照可以先由开发 Agent 根据原文建立，但必须标为“开发诊断／Agent 核查”。只有具备实际独立人工核查记录的结果，才能称为独立人工评估。已用于开发的材料不能重新标为未见测试集。

自然错误、植入错误和合成样本分别统计；机器原始结果、修复后的机器结果和人工修正后的最终结果分别报告。不得通过修改参考答案、移除困难样本或缩小分母来制造提升。

七、本轮建议的量化目标

以下目标用于本轮有明确样本范围的工程验收，不代表总体生产准确率，也不自动改变用户已有放行阈值。

| 评估项建议目标与报告要求   |                                                                                           |
| -------------- | ----------------------------------------------------------------------------------------- |
| 文件处理           | 全部文档状态可解释；可读取、受支持材料的处理完成率至少 95%；阻塞材料全部有可执行的后续路径。                                          |
| PDF 原文覆盖       | 完整恢复的原文区域占比至少 99%；部分恢复计为未完整恢复；逐项列出遗漏，并报告整页无实质遗漏的比例。                                       |
| PDF 文字         | 字符错误率 CER 不超过 1%，同时报告 WER；关键数字、单位、日期、符号和否定表达在样本中全部正确。                                     |
| 表格与关系          | 单元格文字正确率和行列／合并位置正确率分别至少 98%；选定阅读顺序、脚注、标题及跨页关系全部正确，并报告整表成功率。                               |
| Requirement 判断 | Precision 至少 95%，Recall 至少 90%，建议性条款 Recall 至少 90%，给出明确判断的比例至少 90%。                       |
| 原文关联与拆分        | 样本中的来源、版本、编号和原文片段关联全部正确；无编造及重复计数；临时子项拆分正确率至少 90%。                                         |
| 验证器与人工分流       | 自然错误检出率至少 90%，已观察到的关键错误全部被明确定位；有效提示 Precision 至少 80%；十二个植入错误全部检出并正确分流，对应对照误报不超过一个。        |
| 安全自动通过         | 初始改进目标为符合资格的冻结样本中至少 10% 能够安全自动通过；全部自动通过样本均进行原文核查，观察到的正确率为 100%，且没有静默关键错误。有效证据与现有放行规则仍须满足。 |
| 人工负担           | 报告实际任务量、比例和操作量；重复或冗余提示争取减少至少 20%，不隐藏未解决事项，不增加独立的必要审核任务。基线没有冗余时，要求保持零冗余。                   |
| 操作性能           | 声明设备和样本条件下，列表读取 p95 不超过一秒、已缓存证据读取及持久保存分别不超过两秒；普通无锁导出和解除锁定后的恢复分别争取在六十秒内完成。                 |

Precision 和 Recall 必须写明分母。真实正例被系统保留为“不确定”时，在运行效果的 Recall 中计入未找回，不能通过大量弃权提高表面准确率。

自动通过率分别报告 A、B 和端到端结果。若仍为零，应明确说明自动化目标未达成，自动通过正确率属于无样本，不能写成百分之百。不得为达到 10% 而降低用户阈值或绕过证据要求。

自然错误样本为零时，自然错误检出率记为未测，不能用植入错误补齐。每项百分比同时提供原始数量、适用范围和必要的不确定性说明，不能把同一文档的大量字符当成大量独立文档。

每项结果使用 PASS、FAIL 或 UNMEASURED，并绑定版本、方法、分子、分母、证据和下一步。缺少必要测量不能记为通过。

八、人工工作量如何报告

先建立内部条目与真实审核任务的对应关系，再计算人工比例。不能直接把所有数据库行数当作人工工作量。

至少区分：

- 机器已解析的内容；
- 机器自动通过的内容；
- 需要人工查看的独立任务；
- 查看后仅需确认的任务；
- 查看后确需修正的任务；
- 因来源或获取问题阻塞的任务；
- 尚未人工查看、结局未知的任务。

“需要查看”是分流需求，“仅确认”和“实际修正”是查看后的结果，不能作为互不相交的总量简单相加。

报告人工问题可能影响的范围，包括同页、整表、共享上下文和下游 Requirement，以及修正后需要重审的条目数。

有真实观察记录时，报告每项及每百项的人工耗时和操作数；没有真实审查员计时，就明确标为未测。开发时间、工具等待时间和估算时间单独列出，不能充当实际人工工作量。

九、Canva 技术演示

最终演示成果只交付一个可编辑的多页面 Canva 设计及可打开的链接。无需导出 PowerPoint 或 PDF。

页面数量以清楚完整为准，初始按约二十四页组织。总览与细节分开展示，不将所有信息压进一张图。

总体架构图必须采用上、中、下三个横向层次：

上层：统一人工审查。\
横跨 System1、A、B，说明各系统向人工提交什么、为什么提交、带有什么证据，以及人工决定和修正如何回流至所属系统、写入历史并触发下游更新。

中层：系统核心处理。\
展示 System1 → System2A → System2B 的主流程、各阶段职责、交接材料和字段。System3 仅作为未来接口边界。

下层：外部 API／多智能体增强。\
同样横跨各系统，说明接入后能够增强哪些功能、调用哪些现有程序入口、发送哪些证据和返回哪些建议。明确区分已经实现、尚未启用、尚未验证及仅属设计的部分。使用清晰的图例和虚线表达未启用路径，并画明请求与结果返回的方向。

人工审查和多智能体增强都属于跨系统能力，不能画成某个系统末尾的一个串行步骤。产品运行中的多智能体不能擅自修改原件、覆盖人工决定、降低门槛、自行修改程序或部署；其结果仍通过现有验证和人工回路。可选 API 增强不得挤占本轮本地基础系统的交付。

其余页面必须完整解释：

1. 各系统内部的处理模块、流程、分支、失败状态和人工介入点。
2. 实际工程技术方案，包括程序边界、环境、解析器、OCR、表格处理、数据库、原件、Canonical、修正覆盖层、版本依赖、重试恢复与后台同步。
3. 每个系统实际 Excel 展示的内容、工作表、状态及字段，哪些字段交给下一系统或最终交付。A、B 共用工作簿时如实说明。
4. 人工任务的实际信息、置信度来源、分流理由、未知范围和处理回流。
5. 自动处理与自动放行的区别，以及如何检查机器没有报警的错误。
6. 工作台帮助审查员减少操作的设计，区分已实现机制与已经测得的节省效果。
7. 当前功能完成度、真实质量数据、人工负担、性能、限制和未达标事项。
8. 可运行演示步骤、交接说明和下一阶段按证据排序的改进计划。

每一页都必须进行实际视觉检查。检查文字是否可读，是否发生重叠、截断，节点是否对齐，留白是否足够，箭头起终点与方向是否正确，线条是否穿过文字或产生难以理解的交叉，箭头大小和线宽是否与图形比例协调。

所有最终页面必须检查，未解决的意外重叠、截断、不可读文字和错误连线为零。修改后重新检查受影响页面。关键图文应能单独编辑，不能用整页截图冒充可编辑工程图。生成成功、导入成功或对象数量正确均不能替代视觉验收。

十、八小时执行计划

0:00–0:30，状态与范围核实。\
确认运行版本、功能接线、数据保护范围和历史证据；冻结材料与样本，记录计时、目标版本、已有失败尝试，建立功能矩阵和 Canva 内容提纲。

0:30–2:00，形成第一轮真实基线。\
建立原文对照，完成可测范围的解析、判断、验证器和人工分流统计。最迟在第二小时给出第一轮真实数字，并选出一至两个影响最大的根因。

2:00–3:30，集中修复。\
优先处理静默关键错误、主流程阻塞和显著增加人工工作的根因。用最小实验验证修复，对比相同冻结样本和未修改对照。

3:30–5:00，验证可运行闭环。\
完成十六类场景的验证或有效历史证据复用，检查人工操作、持久化、下游重审、离线运行、Excel 同步、恢复和性能，准备演示证据。

5:00–6:00，冻结候选版本与复测。\
固定代码、配置、样本、参考和输出版本，重测受影响指标，核对原件与历史，完成量化报告和交接说明。

6:00–7:30，完成 Canva 与最终交付。\
按已冻结的事实制作一个多页面设计，逐页检查并修正，核对演示数字和报告一致性，最后至少保留三十分钟用于最终视觉复查与交接。

最后三小时必须用于版本、复测、报告和展示，不得全部消耗在 PDF 优化上。只有现有证据和工具条件允许时才提前至六小时结束，不能删掉必要验收来压缩时间。

十一、失败诊断、调整和持久执行

采用 adaptive planning 和 rolling-horizon planning。近期步骤详细规划，后续步骤根据新证据调整。

每次失败按以下顺序处理：\
观察问题 → 区分症状和根因 → 提出有区分力的假设 → 进行低成本实验 → 实施最小干预 → 在相同样本和对照上验证 → 决定保留、调整或回退。

每个 checkpoint 记录正在验证的假设、证据、成功标准、失败含义，以及 CONTINUE、ADJUST、BACKTRACK、PIVOT 或 STOP 的决定。

同一根因连续三轮无效尝试后停止该路径，已有历史尝试计入。只有新证据改变诊断、存在新的有界实验且仍有剩余时间，才恢复尝试。更换会话、换一种相似修改或重新命名问题不能重置次数。

可验证的人工替代路径可以保留功能可用性，但不能抹掉机器质量或自动化目标未达成的事实。不得通过删除困难样本、放宽门槛、隐藏失败或更改指标名称制造完成。

使用项目既有状态和计划文件保存目标版本、开始时间、剩余时间、冻结样本、当前候选版本、指标结果、失败尝试及下一步。跨会话继续时读取这些记录，不从聊天印象重新开始。稳定规则、当前状态、执行计划和历史证据分别维护，避免重复事实源。

遇到确需用户决定或外部输入的问题，说明最小必要事项，同时继续完成不依赖该输入的工作。在已有授权内持续推进，不停留在建议、代码生成或单独的测试通过。

十二、最终交付与完成判定

最终必须提供：

1. 一个明确标识版本、能够运行、具备启动与恢复说明的系统版本或受限候选版本。
2. 功能完成度矩阵及十六类关键场景的验证证据。
3. 可复查的量化报告、原始统计表、样本清单和版本记录。
4. 一个完整、可编辑并经过逐页视觉审查的 Canva 设计链接。
5. 简洁的演示和交接说明，讲清已经完成什么、哪些尚未完成及下一步为何优先处理这些问题。

分别报告功能与完整性、样本范围内的质量、安全自动化程度、交付材料四类结论。完整目标只有在适用的硬性功能要求、采用的质量目标和交付要求均有证据通过时，才能标记完成。

若八小时结束时仍有必要指标 FAIL 或 UNMEASURED，保留最新可用版本，标明“受限候选版本，整体目标未完成”，列出具体缺口、已尝试路径和下一项能够改变结论的实验。不得因时间用尽或汇报材料写完就宣布达标。

本轮最终需要让用户能够清楚地说明：这个系统现在能做什么，机器处理质量如何，哪些情况会交给人工，人工会得到哪些信息、承担多大工作量，自动部分的可靠性凭什么成立，以及下一阶段应当优先改进什么。
