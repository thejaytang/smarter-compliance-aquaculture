# Human Review Contract

The directory/storage migration preserves the existing interface and source semantics.

- One continuously editable extracted document; stable block IDs and exact source references. Current text and Changes are reading/editing modes, not saved versions. Many blocks may support one Requirement, ordered by source position.
- One Rx identifies one Requirement entry. Its header toggles disclosure except for action buttons; coloured source text is selectable only while editing and does not toggle. One entry opens at a time. Locate synchronizes the three source/structuring views. Remove requires confirmation.
- Selection exposes Group and grammatical fields. Groups alone carry exact/inclusive-range quantities. Only an explicit Group relationship holds a source-expressed connector such as `including`; it is metadata, not a counted item. AND/OR quantities preserve their stored semantics. Do not infer extra NOT operators from wording.
- Exception and Subrequirement link complete other Requirements. Preserve explicit quantities on linked sets, ordered entries and per-link removal. Removing a Group removes its included elements; no silent flattening.
- The fourth pane follows only the selected third-pane Requirement and defaults to reading Scope/A, Condition/B, Demand/C and linked concepts. Edit exposes the existing rule and concept controls; Done editing changes presentation only. Program-combined third-column wording is visibly separate from the human interpretation in each card; it preserves recorded words/groups/quantities without semantic inference or model calls. Copying it as starting text is explicit. Evidence holds earlier explanations and quotations; supporting notes belong to their card. Shared object/period fields are under Check context. One explicit Generate AI candidates button requests all three cards together; each candidate requires separate Approve before replacing draft content. More holds source-context management, history and advanced data integration; mapping readiness must not appear as semantic-review incompleteness in the default view. Rule-linked local concepts retain stable IDs, types, exact quotations and proposed/confirmed meanings. Neither source Subject nor model output automatically determines Scope. Candidate adoption, explicit save and human confirmation remain separate, and unresolved concept meanings still block confirmation.
- A identifies scoped objects; B selects applicable objects within A; C identifies the same type of objects with evidence of meeting Demand. Their intended check is B ⊆ C in a shared assessment context. Absent conditions, unmapped predicates and missing identity/context mappings remain unresolved. Changes to Logic, context, rules or catalog invalidate mapping confirmation. An unsupported OR/NOT branch blocks the whole affected filter, never just that branch.
- The generated checking chain is derived from saved structured content and check design. A subset expression is a design for later evaluation, not an actual compliance result.
- Individual Scope/Condition/Demand approvals are source- and content-bound records with server-recorded reviewer/time and an optional model candidate run ID. Opening, mechanical projection and ordinary save never grant approval. Changed content or shared context invalidates affected approvals; final confirmation requires all three current, saved approvals. Older saved drafts and their history remain intact, without invented per-card approvals.
- Save, review, candidate acceptance and archive are separate. Unsaved work is page memory. Manual history is append-only after explicit save. Shared visibility does not change creator IDs; history records actual authors.
