**CONFIRMED:** user decision. **PROVISIONAL:** working policy awaiting collaborator confirmation. **PROPOSED:** engineering design offered for validation. **OPEN:** unresolved scope or decision. Alternatives in the third column are comparisons, not authorization to implement them. Confirmed choices do not require another round of approval merely because alternatives are listed.

## 1. Sensitive decision matrix

| Boundary and why it changes the outcome | Current implementation and current chosen design | Other options and their consequences |
| --- | --- | --- |
| **1. Source review scope.** Re-reviewing or silently broadening the source pool changes work, provenance and human authority. | **CONFIRMED:** preserve existing System1 human decisions and unresolved paid/access issues; use already eligible sources for current processing. Source expansion is not a prerequisite. Existing integration already distinguishes eligible intake from source governance. | Re-review every source would add workload and risk overwriting prior decisions. Expand discovery as a separately scoped later capability. It must not bypass governed source admission. |
| **2. Database versus Excel authority.** Two writable masters create inconsistent decisions and versions. | Current System1 still uses Excel business state; System2 already has a workflow database and derived Excel. **CONFIRMED TARGET:** each fact belongs to its owning database or immutable source artifact; workbench writes decisions; Excel is one-way output with no direct-edit import. | Excel as primary store retains file locking and whole-workbook overhead. Bidirectional synchronization needs conflict resolution and adds complexity; it is outside the chosen design. One physical database for all components is optional and is not implied by a shared UI. |
| **3. System1 migration.** Lost history or changed admission alters downstream meaning. | **PROPOSED:** isolated-copy migration, source/decision/history parity, original fingerprints, adapter comparison and rollback evidence before changing the active store. No migration has run in this alignment session. | A fresh database without historical migration loses audit continuity. Long-term dual authority invites divergence. A temporary read-only comparison period can validate the migration without creating two business masters. |
| **4. One workbench.** Fragmented entry points create inconsistent human decisions and unnecessary training. | **CONFIRMED:** one normal workbench for all systems, with separate System1, A, B and future System3 views and counts. The current common workbench is the implementation foundation. | Separate review apps duplicate identities, queues and workflows. Excel review input conflicts with the confirmed one-way Excel rule. A diagnostic-only page may remain, but is not a second human operating process. |
| **5. A fidelity versus early filtering.** Filtering at extraction time can permanently hide context or obligations. | **CONFIRMED:** A retains content, structure, order and auxiliary material regardless of perceived relevance. B owns Requirement selection. Existing extraction and review representations require checking against this all-content target. | Drop margins/notes or extract only likely obligations to reduce volume, at the cost of losing fidelity and recall evidence. Such filters are not the approved A design. Read-only filtered views can aid browsing while retaining full records. |
| **6. Illustration versus scanned text.** A wrong region type can silently exempt real text from verification. | **CONFIRMED:** preserve photographs/illustrations with figure titles as images without in-image transcription; scanned document text still requires extraction. **PROPOSED:** uncertainty about region type is a review issue. Existing routing has native/OCR/mixed paths; reliable coverage is not yet established. | Transcribe every figure as well: broader scope and additional error modes. Treat every image region as opaque: simpler but fails scanned-document fidelity. The chosen distinction is by content role, not file encoding. |
| **7. Whole-table preservation versus Requirement rows.** Early semantic row selection loses shared headers, merged cells and notes. | **CONFIRMED:** A preserves a complete logical table, original image, cell text, row/column/span structure, title and notes. B identifies internal Requirements. Existing PDF code has row-oriented review and repair foundations, so the A/B ownership must be reconciled explicitly. | Image-only tables preserve appearance but force B to recognize them again. Independent flat rows lose shared context. Whole-table plus structured cells is the chosen representation, with rows as structural children rather than A-stage semantic decisions. |
| **8. Table-spanning context.** Wrong cross-page joins or note inheritance can change a requirement even when every word exists. | **PROPOSED:** retain original fragments, verify joins, scope shared values/notes explicitly and preserve local versus table-wide ownership. The current code has bounded repair evidence and unfinished cross-page acceptance. | Flatten text or repeat all nearby notes for every row is easier but can attach incorrect conditions. Repeating verified context in display/export is permissible if authoritative relationships and counting remain unambiguous. |
| **9. Meaning of Requirement.** Excluding recommendations changes recall and downstream interpretation. | **CONFIRMED:** recommendations can be Requirements. **PROPOSED:** retain mandatory/advisory character and source-cited reasoning. Current offline classification uses normative wording and item types, not a fully validated semantic classifier. | Mandatory-only classification is narrower but contradicts this target. Treat every paragraph as a Requirement maximizes apparent recall but shifts unresolved judgment downstream. Site-specific applicability and final compliance remain separate. |
| **10. Parent, children and active splitting.** Splitting changes identities, counts and downstream mapping. | **PROVISIONAL:** keep the original numbered parent intact; add derived requirement subitems and allow active splitting without original sub-numbering. Human collaborator confirmation remains outstanding. Earlier runtime contracts preserve source boundaries and do not yet establish this B behavior. | No subdivision is simplest but can make site/evidence matching coarse. Split only explicit original subitems is conservative. Atomic obligations may improve matching but require a clear independence criterion and shared-condition handling. Preserve original parent text under every option. |
| **11. B subdivision versus System3 semantics.** A split can inadvertently become inferred semantic enrichment. | **CONFIRMED:** System3 is deferred. **PROPOSED:** B subdivisions contain source-bound spans and shared context, not invented actors, thresholds or completed ontology fields. | Perform full actor/action/object ontology in B: broadens the current scope and blurs system ownership. Defer all splitting to System3: simpler B, but differs from the user's provisional working plan and would need confirmation. |
| **12. Independent verification.** Self-consistency can pass even when extraction misses the same evidence. | **PROPOSED:** independently callable original-to-result checker, distinct evidence provenance, original-side coverage and reference-labelled acceptance of the checker itself. Current completeness functions are a foundation, not proof of a finished independent verifier. | Reuse parser output as the sole truth: cannot detect systematic omissions. Rerun the same model: repeated agreement is not independence. A second model/engine can add evidence but still needs human-reference evaluation and correlated-error analysis. |
| **13. Verifier's delivery scope.** An internal checker and a general external product have different interface obligations. | **PROPOSED:** a separable checker interface inside the current workstream; no changes to the other team's project. **OPEN, conditional:** independently delivered multi-parser tool and consumer contract if the other team needs that output. | Tightly coupled internal checks are cheaper but harder to reuse. A fully parser-neutral package needs adapters, version contracts and its own consumer acceptance; do not assume it solely because another team has related work. |
| **14. Confidence and automatic acceptance.** A high unsupported score can hide systematic errors. | **CONFIRMED:** user-configurable stage thresholds. **PROPOSED:** scoped empirical calibration, independent holdout, necessary-component gates and hard blockers. Current calibration plumbing exists; production reliability is not established. | Model self-confidence or majority voting is easy to produce but unsupported as a probability. Weighted averages can hide a critical weak dimension. Conservative gating increases human work unless extraction and evidence improve; report this tradeoff rather than masking it. |
| **15. Error budget and completion.** Optimizing a single aggregate score can conceal critical defects or excessive manual work. | **PROPOSED:** separate parser/verifier metrics, B precision/recall, critical-error blockers, automation coverage and reviewer time. Existing 95% defaults are not proven accuracy. Numerical error tolerances will be proposed from pilot evidence rather than attributed to the user. | Require manual approval for every item: may yield usable data but defeats automation-first intent. Lower thresholds merely to reduce Pending: rejected. Claim zero future errors from a small clean sample: unsupported. |
| **16. Human completion and history.** Recording an action is not the same as resolving the underlying problem. | **CONFIRMED:** a completed decision is durably saved, leaves Pending and appears in Review history; Excel then follows automatically. **PROPOSED:** draft/submission/applied/export states are visibly distinct and unresolved follow-up stays pending. | Move every click to history: hides incomplete work. Wait for Excel before accepting the database decision: adds unnecessary blocking. History can include intermediate actions while the unresolved task remains visible. |
| **17. Changes, re-review and downstream use.** Accepted data can become stale after correction or a new source version. | **PROPOSED:** source/version-bound decisions, dependency invalidation, preserved historical versions and explicit suspension of affected deliveries. Existing System2 contracts contain foundations for this behavior. | Never reopen accepted records risks stale results. Re-review the entire document after every edit increases workload. Dependency-scoped rechecking is preferred but must itself be tested for missed links. |
| **18. Excel freshness and performance.** Frequent full exports can freeze review; stale files can misrepresent decisions. | **CONFIRMED:** automatic one-way synchronization. **PROPOSED:** durable event/dirty marker, background coalescing, consistent snapshots, atomic replacement, visible versions/retries and independent UI reads. Current System2 already exports in the background. | Synchronously rewrite after every decision: freshness is simple but review slows. Manual export only: violates the automatic-sync target. Partial cell updates may help later, but require measured benefit and consistency tests; a visible snapshot is not necessarily a live open workbook. |
| **19. Multi-agent enhancement.** More agents do not automatically mean better evidence or altered human authority. | **CONFIRMED:** optional API assistance invokes program capabilities to improve processing and checking; same thresholds, workbench and human decisions. No autonomous code editing/deployment. Current evidence-suggestion adapters do not establish a complete enhanced multi-agent system. | An API-required pipeline violates the offline requirement. A separate autonomous approval path bypasses the agreed human loop. Self-modifying code agents were explicitly removed from the interpreted scope. |
| **20. External evidence access.** API assistance can require material to leave the local machine. | Existing project boundary requires explicit authorization for external document transmission and preserves confidentiality. **PROPOSED:** allowlisted evidence and recorded provider/version, with failure returning to local/manual processing. No provider is activated by this design document. | Local models may reduce external transfer but add hardware and maintenance needs. Unrestricted whole-document transmission is not authorized. Exact provider, budget and permitted evidence are execution-time decisions, not a current blocker to target definition. |
| **21. Weekly QA sample unit and population.** Sampling only extracted positives misses omitted areas and false negatives. | **CONFIRMED working counts:** Monday System1 5, A 20, B 5; System3 inactive. **PROPOSED:** A checks original-side regions/pages; B includes positive and negative decisions; short pools remain explicit. Existing earlier QA policy needs adaptation. | Pure positive-item sampling is easy but cannot measure B false negatives. Random source pages can find omissions but vary in review effort. Risk-stratified sampling improves difficult-case exposure but its percentages must not be reported as unweighted whole-population accuracy. |
| **22. Calibration labels and ongoing QA.** Unclear reference truth makes scores meaningless; tiny samples cannot establish rare error rates. | **PROPOSED:** independent adjudicated reference labels, frozen calibration/held-out sets and explicit sampling uncertainty; weekly QA is monitoring. **OPEN, conditional:** collaborator reference-label owner and adjudication process when that work is scheduled. | Self-labelled parser/model answers are not independent truth. Reusing the acceptance set to tune methods contaminates evaluation. Human time is needed for a bounded reference set, but does not imply requiring humans to inspect every production item. |

## 3. Engineering-owned choices that do not need another user decision now

- Independent verification metrics, reference-sample design, confidence calibration and a defensible proposal for error tolerances.
- Database schema, migration mechanics, transactions, outbox/dirty-state approach, indexed reads, export batching, snapshot verification and recovery tests.
- UI layout details implementing the agreed original/result comparison and clear task-based review.
- Provisional latency budgets and benchmark workloads, labelled as engineering proposals in the target document.
- Detailed agent roles, provider adapters and offline fallbacks, without assuming external access or automatic acceptance.
- QA stratification and catch-up mechanics, while preserving Monday samples of 5 System1 items, 20 System2A checks and 5 System2B judgments and making shortages visible.

These choices should be justified with a small measurable experiment. They do not become permanent user commitments simply by appearing in a design file. Material changes to confirmed source, human-authority or quality boundaries return for discussion.

## 4. Changes explicitly excluded by the aligned target

No normal direct Excel editing/import, no silent requirement filtering in A, no illustration-text transcription in this phase, no replacement of human decisions by agent consensus, no autonomous program rewriting or deployment, no System3 ontology implementation now, and no blanket re-review of the completed System1 source batch. None of the alternative designs above weakens original-source preservation, confidentiality, existing human history or the requirement for evidence-backed acceptance.
