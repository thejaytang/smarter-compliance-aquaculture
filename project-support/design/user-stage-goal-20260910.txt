完成水产养殖合规项目 Requirement Workstream 本阶段的实施与验证，交付一个功能完整、稳定可运行、交互畅通，并能通过“机器处理＋必要人工审核”完成实际工作的系统，覆盖 System One、System Two A、System Two B 和统一人工工作台。

对于反复修复仍无法可靠解决的自动化质量问题，可以提高人工审核比例，并将进一步优化列入未来提升待办。人工处理路径必须实际可用，不能仅把问题放入 Pending，却没有定位、修正、保存和继续处理的办法。

### 2. 系统目标与职责

**System One：来源治理**

保留已有来源身份、原件、版本、纳入结果、人工决定和历史记录。不重新发起已完成人工审核来源的整批审核，不擅自扩大来源发现范围。付费获取等未解决事项继续保持 Pending。

将业务状态保存在所属的本地关系型数据库中，Excel 作为单向同步生成的来源台账。迁移前在隔离副本中验证数据和历史完整性，并保留恢复路径；若迁移已经完成且有可靠证据，则核对现状并沿用，不重新迁移。

对于缺少正文、原件不完整或不可读取等来源问题，应在工作台明确展示原因、受影响范围和下一步处理方式，保留已有有效版本。不能将目录、摘要或错误页面当作完整正文继续交付。

**System Two A：忠实还原原文**

尽可能完整、准确地还原来源的内容、结构和阅读顺序，不按是否属于 requirement 提前筛除内容。保留页码、页眉页脚、标题、附注等辅助内容及其原文位置。

区分文本型、扫描型和混合 PDF 的页面与区域，主动检测疑似遗漏。检查范围必须包含原文中尚未对应任何抽取条目的区域。

照片和示意图整图保存，关联图号、图题和位置，暂不识别图内文字。扫描正文不适用这一豁免；扫描识别不可靠时，应提供原图定位、人工录入和修正路径。

表格整体保留原图、标题、表注及脚注，同时支持保存可读取的单元格内容、行列、合并关系和跨页联系。A 中的行列划分属于结构还原，requirement 识别交给 B。

对于机器无法可靠还原的内容、表格或跨页关系，允许由人工补充或纠正。修正结果必须保留原文关联，并进入后续有效结果和输出。自动还原不够准确可以成为已知局限；人工也无法修正或继续处理，则仍属于本阶段需要解决的功能缺陷。

沿用已有合理的 HTML、XLSX 处理能力和受控来源接口，不因为重点处理 PDF 而丢弃其他已支持格式。

**System Two B：Requirement 识别**

基于 A 已查验的内容及必要上下文，判断哪些属于 requirement，包括建议性条款。A 的查验可以来自有依据的机器放行，也可以来自记录完整的人工确认。

每个结果保留原文依据、原编号、来源版本、位置和相关上下文。支持人工纠正误收和漏判，包括将机器判为非 requirement 的内容改为 requirement。

暂按完整原文编号条目保留父项，并关联 requirement 分项；允许原文无明确子项时主动拆分。生成编号与原文编号必须区分，不得编造原文没有的要求，也不得重复计算父项和分项。

拆分粒度、父子项交付和计数方式仍待同伴确认。在确认前，采用明确标注、可逆、可配置的临时策略，并允许人工调整。不将临时策略视为永久规则，也不因永久规则尚未确定而无限推迟本阶段完成。

自动分类或拆分不可靠时，可以转人工判断，不要求本阶段所有内容都能自动正确分类或拆分。

**System Three**

暂不实施动作、对象、条件等 ontology 语义结构化。保留后续接口边界，不扩大到 Evidence 提取、具体场地匹配或最终合规判定。

### 3. 统一人工工作台与数据流

三个系统共用一个正常人工入口。所有日常审核、补充信息、纠正和抽查都在工作台完成，不转移到 Excel、数据库编辑器或工程脚本中操作。

工作台明确展示待决定事项、进入人工队列的原因、机器置信度及原文证据。内容审核采用左侧原文、右侧抽取结果及上下文的布局。

对于遗漏、错误文本、表格结构或关联问题，人工应能够：

- 找到相关原文位置及必要上下文；
- 理解需要作出的决定；
- 复制、输入或修正缺失及错误内容；
- 确认或调整必要的结构和关联；
- 保存决定，看到有效结果更新及后续处理状态。

不要求实现复杂或理想化的编辑器，但必须提供足以完成实际工作的操作方式。

处理流程为：

工作台确认完成 → 数据库持久保存决定和历史 → 已解决事项从 Pending 移入 Review history → Excel 自动同步。

草稿、提交失败或仍有未解决问题的事项不得显示为完成。原文或内容改变后，应重新检查受影响的下游结果，同时保留旧版本的审核历史。

机器不确定性可以通过明确的人工查验得到解决。缺少机器校准分数本身，不应阻止已经完成人工确认、且没有未解决实质问题的结果继续进入 B 或交付。

数据库保存权威业务状态和人工决定；原始文件、图片及不可变源事实可以保存在受管理文件中并建立关联。Excel 只用于查看与交付，禁止正常直接编辑，不提供 Excel 修改回写业务数据的路径。

采用后台合并更新、版本标记、失败重试和一致快照。工作台日常读取及决定保存不得等待整个 Excel 重写。明确区分决定已保存、Excel 待同步、同步完成和同步失败。

系统整体可以完成本阶段交付，同时保留尚待用户处理的业务 Pending。业务 Pending 的存在不等于系统未完成，但这些事项必须有清楚、可操作的处理路径。

### 4. 原文验证、Confidence 与人工兜底

保留并完善可独立调用的原文验证模块，以原始文件和抽取结果为输入，输出可定位的疑似差异、依据、严重程度及未验证范围。

本阶段要求验证模块能够运行、暴露已知问题和未验证范围，并与人工工作台衔接；不要求其自动发现所有错误，也不要求先证明其对所有材料都具有高准确率。

分别关注：

- 内容遗漏和文字错误；
- 结构、顺序、表格及脚注关系错误；
- 验证器漏报和误报；
- requirement 判断的 precision 与 recall；
- 原文关联及分项正确性。

在现有材料和投入允许的范围内收集这些质量证据，优先验证会影响实际使用的错误。全面独立质量评估、正式置信度校准和大规模 held-out acceptance 可以作为后续提升工作，不作为本阶段功能交付的统一前置条件。

开展正式质量评估时，仍须使用独立人工确认的参考样本，明确分开开发、校准和 held-out acceptance 样本，并分别报告自然错误与人为植入的测试错误。已有开发样本不得重新宣称为未接触的验收样本。

模型自报置信度、多智能体一致意见、重复调用同一方法、格式检查通过或回归测试通过，均不能单独证明原文正确。

由工程设计评分指标和校准方法；由用户设置各阶段放行阈值。已有默认阈值不代表已达到相应准确率。没有有效校准时，应显示未知或未校准，不编造分数。

分别呈现 A 的内容、覆盖、结构和顺序，以及 B 的分类、关联和拆分状态。关键遗漏、错误数字或否定词、表格错位、关键脚注关系错误等明确问题，不能被平均分掩盖。

缺少有效评分、证据冲突或存在未解决问题时，进入人工工作台。人工修正并查验后，可以按人工确认路径放行；未解决的明确错误仍不得作为已确认结果交付。

允许本阶段提高人工审核比例，尤其用于反复优化仍不可靠的材料和功能。不设未经确认的最低自动化比例作为完成门槛，但应保留并验证已有基础自动处理能力，不能将整个系统简化为纯人工录入工具。

记录代表性任务的自动处理比例、人工操作步骤和耗时，用于识别明显不可用的流程。人工比例较高本身不构成本阶段失败；无法完成、操作不清楚或需要反复依赖开发 Agent 才能完成，则属于需要改进的功能问题。

### 5. 每周人工抽查

实现以下每周一抽查规则：

- System One：抽查 5 条来源治理记录。
- System Two A：抽查 20 个原文内容检查单元。
- System Two B：抽查 5 个 requirement 分类判断。
- System Three：本阶段不启用抽查。

以上是每周抽样数量，不是日期。

A 的抽查范围必须包含可能完全漏掉的原文区域，不能仅从已有抽取结果中抽样。B 同时覆盖判为 requirement 和判为非 requirement 的结果。

样本不足、抽查未完成及发现的问题均须明确记录，任务进入统一工作台。问题修正和后续复核沿用正常人工处理路径。

本阶段验证抽样、持久保存、任务进入工作台、问题跟进及历史记录等机制，不要求等待多个自然周或积累足够统计样本后才完成任务。

实际定时机制的启用遵守项目授权边界。若尚未获准启用，但机制已完成隔离验证并具备清楚的启用方式，可以将“实际启用”列为待授权事项，不阻止其他已完成部分的阶段性交付。

每周抽查用于持续监测，不直接证明高准确率。

### 6. 无 API 基础模式与可选增强

不接外部大模型 API 时，本地处理、检查、人工修正和输出流程仍须可运行，这是本阶段必须完成的能力。

保留合理的 API 和多智能体增强接口。接入 API 后，增强功能调用现有程序进行处理、核查和判断，沿用相同的数据、置信度门槛、人工回路和历史记录。

API 不可用或调用失败时，保留已有结果，清楚显示失败，并返回本地或人工处理路径，不阻断基础工作流。

产品运行中的多智能体不得自主修改程序代码、部署变更或绕过人工决定。这一限制不禁止承担本 goal 的开发 Agent 在授权范围内修改和测试工程代码。

外部模型启用和材料发送遵守既有授权及保密边界。

实际外部模型接入、多智能体效果优化和增强效果比较属于可选后续工作，不作为本阶段完成的必要条件。若开展比较，应使用相同冻结样本，报告质量、人工负担、耗时和成本。

### 7. Checkpoint、验收与本阶段完成标准

优先验证一条小范围实际闭环：

发现或报告原文问题 → 定位原文 → 人工补充或修正 → 数据库保存决定和历史 → 有效结果更新 → 相关 B 判断重新检查 → Excel 自动同步。

优先复用已有可靠证据，只补充缺失环节。代表性检查应涵盖文本、扫描处理路径、复杂表格、跨页关系以及已有 HTML、XLSX 能力，但不要求每类材料都自动处理正确。

优先使用现有真实来源。缺少某类真实样本时，可以用明确标注的测试材料验证功能机制，将真实材料适用性列为待验证事项；不得将测试材料的结果宣称为真实来源准确率。此类证据缺口不自动阻止本阶段整体功能交付。

**本阶段必须完成：**

- 主要系统职责和必要功能齐备，正常入口和主要交互畅通；
- 已有来源身份、原件、版本和人工历史得到保留；
- 数据库作为权威业务状态，Excel 单向同步且无正常回写路径；
- 人工能够完成原文查看、定位、补充、纠正、确认和历史查询；
- 决定可靠保存，相关下游结果正确更新；
- 草稿、失败、Pending、已保存及同步状态准确，不出现虚假完成；
- 重试、重启和必要恢复不会丢失决定、重复应用操作或覆盖较新的结果；
- 无 API 时，代表性任务仍能通过机器与人工配合完成交付；
- 每周抽查机制及问题跟进路径可运行；
- 在声明的设备和代表性材料上，没有明显阻断日常使用的性能或交互问题。

性能验证以实际可用为先。已有数值预算属于工程建议，不因轻微偏离未经用户确认的预算而无限优化；明显卡死、无法保存、无法同步或不能恢复的问题仍须解决。

**允许作为已知局限或未来提升事项：**

- 困难材料的自动抽取、结构还原及判断准确率；
- 尚不充分的独立参考标签和真实样本覆盖；
- 全面 precision、recall、验证器误报漏报评估；
- 正式置信度校准及 held-out acceptance；
- 进一步降低人工审核比例和人工耗时；
- 同伴尚未确认的永久拆分、父子交付和计数规则；
- 可选 API、多智能体增强及其效果比较；
- 不影响主要工作流的低影响显示、体验或性能优化。

当必须完成的功能和可靠性要求已有适当证据，代表性任务能够通过“机器处理＋必要人工审核”完成实际交付，且不存在阻断主要流程或危及数据完整性的未解决问题时，可以认定本阶段 goal 完成。

不要求把所有现有来源和全部待审核条目处理完毕，也不要求清空所有 Pending 或未来提升待办。

每个 checkpoint 简要报告已验证范围、证据、失败、未解决事项，以及继续、调整或延期的决定，并更新所属系统的状态文件。不要将维护计划、增加测试数量或生成更多报告本身当作主要进展。

### 8. 反复修复的停止条件与未来提升待办

同一问题默认最多连续进行三轮有明确假设和验证结果的修复。已有历史尝试应计入判断，不因切换会话、重命名问题或新建 checkpoint 而重新开始计数。

若经过多轮尝试仍无明显改善，应判断：

- 是否阻断主要功能；
- 是否存在实际可用的人工处理或替代路径；
- 是否影响数据完整性、历史保留或结果状态真实性；
- 继续投入是否有明确的新证据和合理收益。

对于已有可用人工路径、且不危及数据可靠性的自动化质量问题，应及时停止优化，列入未来提升待办，继续完成其他必要功能。

只有出现新的有效证据，表明存在明确且成本合理的解决路径时，才继续追加修复。不要因为“还能再试一次”就无限循环。

对于数据丢失、错误覆盖、虚假完成、主要流程无法继续等问题，不能仅靠列入待办来宣布完成。应优先采用更简单、可验证的实现或替代交互修复；若仍无法解决，准确报告阻断点和最小所需输入。

未来提升待办至少记录：

- 问题及影响范围；
- 当前可用的人工处理或替代方法；
- 已尝试的方案和结果；
- 延期原因；
- 重新启动改进所需的条件或证据。

最终交付报告分别列出：已完成并验证的功能、已知局限、需要人工介入的情况、待授权或待提供的输入，以及未来提升待办。

明确区分“系统已完成本阶段功能交付”“某份来源已完成处理”和“自动准确率已通过独立验收”，不得混为一谈。
